# OpenPLC setup

One-time setup for the cell PLC. After this, `./scripts/start_cell.sh` brings
everything up on its own.

Bringing up a PLC link has a lot of small steps and exactly one symptom when
any of them is wrong: nothing happens, and nothing reports an error. So work
through these in order.

## What you are building

```
   browser HMI ──Modbus TCP──► OpenPLC ──Modbus TCP──► MuJoCo sim
   operator panel               cell PLC              robot controller
                    :502                     :5020
```

OpenPLC plays two roles at once, which is the point of the exercise:

- **Modbus slave** on port 502 — the operator panel polls it for cell state and
  writes its buttons there.
- **Modbus master** — it polls the simulation at `host.docker.internal:5020`
  for robot status and writes permits back.

The simulation runs on the Mac rather than in a container because it needs the
GPU for rendering. `host.docker.internal` is how the container reaches back out
to it.

## 1 — Docker

OpenPLC's runtime does not run natively on macOS, so it runs in a Linux
container. Install **Docker Desktop for Mac, Apple Silicon build** and start
it; no account is needed. Wait until the whale icon stops animating.

Check you have the native build, not the Intel one — an emulated runtime adds
scan-time jitter that is very easy to mistake for a Modbus fault later:

```bash
docker info --format '{{.Architecture}}'      # expect aarch64 / arm64
```

> If `docker` is not found but Docker Desktop is clearly running, open a **new**
> terminal. Docker Desktop adds `~/.docker/bin` to your shell profile, and
> shells opened before the install will not have it.

## 2 — Start the container

```bash
docker compose -f plc/docker-compose.yml up -d
```

The first run builds OpenPLC from source, which takes several minutes. That is
deliberate: the published images are amd64 only, and building here gets a
native arm64 runtime. Watch it, or diagnose a failure, with:

```bash
docker compose -f plc/docker-compose.yml logs -f
```

## 3 — Log in

Open **http://localhost:8080**. Stock credentials are `openplc` / `openplc`.
Change the password under **Users** once you are in.

## 4 — Enable the Modbus server

**Settings** → tick **Modbus**, port **502** → **Save changes**, then restart
the PLC from the dashboard. This is the operator panel's link into the PLC;
without it the HMI has nothing to talk to.

## 5 — Add the slave device

This is the PLC's link out to the robot. **Slave Devices → Add new device**:

| Field | Value |
|---|---|
| Device Name | `qd_sim` |
| Device Type | **Generic Modbus TCP Device** |
| IP Address | **an IP address, not a hostname** — see below |
| IP Port | `5020` |

> **Do not type `host.docker.internal` here.** OpenPLC's Modbus master is
> libmodbus, and `modbus_new_tcp()` takes a dotted-quad address — it does not
> resolve hostnames. A hostname fails with
> `Connection failed on MB device qd_sim: Invalid argument` in the runtime
> logs, which reads like a malformed register block rather than a name that
> could not be looked up. Get the address with:
>
> ```bash
> docker exec qd_cell_plc getent ahostsv4 host.docker.internal
> ```
>
> On Docker Desktop it is typically `192.168.65.254`. It can change if Docker's
> networking is reconfigured, so if the device goes offline later, re-check it.

Then the register blocks. **The sizes matter more than they look** — OpenPLC
derives every `%`-address from them, so a wrong size does not produce an error,
it silently shifts every address after it:

| Block | Start | Size |
|---|---:|---:|
| Discrete Inputs (%IX100.0) | 0 | **32** |
| Coils (%QX100.0) | 0 | **16** |
| Input Registers (%IW100) | 0 | **32** |
| Holding Registers - Read (%IW100) | 0 | **0** |
| Holding Registers - Write (%QW100) | 0 | **16** |

Holding-Read is **zero on purpose**. Everything the PLC reads from the robot is
already an input register; a second copy would be a second source of truth for
the same words.

These numbers come from the code — see `docs/PLC_TAGS.md`, generated by
`scripts/gen_plc_docs.py` from `qd_plc/tags.py`. If you change a register map,
regenerate and retype this table.

**Save, then restart the PLC.** Slave devices are only picked up when the
runtime starts.

### Or let the script do it

Steps 4 and 5 can be done for you, with the block sizes taken from
`qd_plc/tags.py` instead of retyped, and the IP resolved for you:

```bash
venv/bin/python scripts/plc_configure.py            # preview
venv/bin/python scripts/plc_configure.py --apply
```

Add `--replace` to rebuild a device that already exists. Doing it by hand once
is worth it to see what the fields mean; after that, the script removes the
main source of error.

## 6 — Load the cell logic

`scripts/start_cell.sh` does this for you on a fresh container, but to do it
yourself:

```bash
venv/bin/python scripts/plc_upload.py plc/st/cell_control.st --start
```

That uploads `plc/st/cell_control.st` — the Structured Text this cell actually
runs — compiles it, and starts the runtime.

## 7 — Confirm it works

```bash
./scripts/start_cell.sh
```

It reports `parked at G0, PLC sees it, ready to start` once the PLC can see the
robot and every interlock for a fresh start is satisfied. If it instead reports
a fault, the panel's **Reset** clears one left over from a previous run.

## Things that will bite you

**`%IX` and `%IW` cannot be written by an ST program.** They are inputs. In
OpenPLC that space also belongs to the master mapping. So all PLC-to-HMI status
lives in coils and holding registers, with an ownership split by address range.
Get this wrong and the HMI reads zeros forever with no error anywhere.

**Everything on the wire is a 16-bit integer.** No floats, no units. `8.42 mm`
travels as `842`. Watch signedness: `TILT_DEG` goes negative and must be `INT`,
while `SIM_TICK` counts past 32767 and overflows `INT`, so it must be `UINT`.

**Avoid `STRING` in ST entirely.** OpenPLC's support is poor. That is why the
wire carries codes and the HMI owns all the operator-facing text.

**Two MATIEC quirks that cost real time**, both found the hard way here:

- *Located and plain variables cannot share a `VAR` block.* Once a block
  contains an `AT %...` declaration, every entry in it must be located; the
  others are reported as `invalid located variable declaration`, pointing at
  perfectly ordinary lines. Give internals their own `VAR` block.
- *Three or more function-block instances in one comma-separated declaration
  segfaults the compiler.* `a, b : R_TRIG;` is fine. `a, b, c : R_TRIG;`
  crashes `iec2c` outright — no line number, no diagnostic, just
  `Segmentation fault`. Declare one instance per line.

**Restart the PLC after changing slave devices or settings.** Neither is picked
up while the runtime is running, and the symptom is that your change appears to
have done nothing.

**Bind the sim's slave to `0.0.0.0`, never `127.0.0.1`.** From inside a
container, loopback is the container's own loopback, so the connection is
refused and OpenPLC shows the slave device as offline with no explanation.
Everything here binds `0.0.0.0` already.

**Only OpenPLC writes Map A; only the HMI writes Map B's command range.**
Poking the sim directly while the PLC is running produces a permit race that
looks exactly like a PLC bug. Stop the PLC first.

**The sim runs far faster than OpenPLC polls.** A whole phase can pass between
two scans. This is handled — conditions latch until acknowledged, and permits
carry a sequence number so a stale one cannot release the wrong gate — but it
means that between gates the PLC is an observer, not a controller. If you need
finer control, add a gate; you cannot poll your way under OpenPLC's scan.
